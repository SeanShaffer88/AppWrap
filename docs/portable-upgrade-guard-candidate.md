## Minimal module contract

One small original MIT native Win32 executable, built once with verified installed SDK/compiler and shipped with source, license, build recipe and hashes. No runtime compiler, .NET dependency, service, driver, DLL injection, network or installer-of-its-own. Bundle helper as trusted AppWrap build resource; generated NSH embeds it with NSIS `File` into `$PLUGINSDIR`, invokes it directly with `ExecWait`, inspects exit and aborts installation before payload mutation on any nonzero result. Restore `$OUTDIR` after helper extraction. Use installer-native friendly error explaining that the app could not close and user may close it/retry. Do not continue with warnings after failure.

Prefer an x86 helper after verifying the installed x86 compiler/SDK/link libraries; this preserves ordinary x86 payload support on x86 and x64 Windows. QueryFullProcessImageName with limited-query handles is the appropriate cross-bitness image identity API; do not rely on x86 PSAPI module enumeration to inspect x64 targets. AppWrap creator being x64 does not make every generated payload package x64-only. Use ordinary supported compiler startup and `/MT` static CRT, preserving default security checks (including `/GS`) and warning diagnostics; do not invent CRT-free startup or disable checks to reduce size. Record actual architecture, flags, CRT/Microsoft redistribution/provenance and supported host limits. Build-time compiler is a development dependency only. Independent Auditor must review native helper code before its first process-action host execution.

Helper input: selected absolute installation root, generated safe launcher-relative filename, validated source-relative payload executable path and a bounded timeout constant (e.g.10seconds). These are discrete quoted arguments; no command shell. Root is runtime `$INSTDIR`, not build-source root, AppId-derived default directory or arbitrary directory enumerated beforehand. Payload path is fixed `App\Payload\<validated-relative-exe>`. Paths must be absolute/canonical where applicable, local supported Windows paths, no traversal/device/UNC/ADS/reparse aliases. Reject unsupported or ambiguous paths. Do not interpret text as script, options or extra executable targets.

Helper result uses fixed documented numeric codes:0 = no matching processes remain and closure completed; nonzero separately identify invalid/unknown identity, denied inspection, timeout, or Windows operation error. No private user path/network telemetry logging; optional bounded diagnostic text only to caller capture. Installer can map all failures to one plain message while retaining code in details/log. Helper has no product UI and does not persist state.

## Process ownership and closure algorithm

Resolve exact expected launcher and payload executable paths under the **selected** root. Validate existing root/components against reparse links; compare Windows canonical final image paths consistently, case-insensitively, without accepting prefix matches or confusing sibling folders. A missing target means that target has no valid installed image to close, not permission to search by name elsewhere.

Use bounded Toolhelp enumeration with candidate basenames solely as an efficiency filter, then open each candidate with minimum query/synchronize rights and obtain its full image path. Only an exact expected path qualifies. Hold process handles and capture PID/start time; revalidate process identity before any window action. A same-name process from a foreign directory must remain alive and unmodified. Unreadable potentially matching process identity must not be guessed: fail closed with an actionable identity/permission error. Do not elevate to inspect/close it.

Collect **all** exact payload instances, including direct launches without root shim, and all exact root-launcher instances. Send graceful WM_CLOSE only to top-level windows belonging to verified payload PIDs, with bounded SendMessageTimeout/PostMessage semantics and identity recheck. Never use process-name close/kill, TerminateProcess, taskkill, WMI termination, global window title matching or arbitrary process-tree termination. No UI window means no proven generic graceful-close method; wait boundedly then fail.

Wait for payload handles to exit; then wait for matching root shims, whose ExecWait should finish naturally when their child exits. Do not close/terminate the shim first while payload still runs. If root shims remain after all matching payloads exited, graceful WM_CLOSE may be attempted only on their verified windows and still within total timeout. Close every acquired handle on all paths. Re-enumerate exact target paths immediately before success to detect new instances; bounded retry/overall timeout prevents indefinite work. This cannot guarantee an external launcher will not start a new process after return; do not claim a universal race-free execution barrier.

No external/user process may be force-killed to pass the test. If graceful closure is refused or app has unsaved-work modal prompt, guard fails before installed payload/Data mutation. The selected installation root may remain as an empty created folder from upstream SetOutPath; report that preparatory footprint accurately. Installer cancellation before Install must never close the application. Once the guard runs, closure is an intentional part of the user-initiated install, but no automatic restart is added.

2. No-process fresh install passes and payload/hash inventory matches.

6. Deliberately uncooperative/headless fixture reaches bounded timeout and installer aborts before any existing payload/Data hash changes; old app remains running, no forced kill, evidence/owned recovery distinct from test pass. Invalid path/reparse/denied-identity cases fail closed.

This candidate intentionally scopes graceful-close support to the selected main executable and AppWrap root launcher. Arbitrary child executables, services or self-restarting programs are not assumed supported.
