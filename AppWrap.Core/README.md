# AppWrap.Core

`PackageNaming.GetFileName(name, version, mode, style)` is the canonical pure naming API. `PackageNamingStyle` offers `NameVersionSetup` (default), `NameOnly` and `NameSetupVersion`; `Labels` supplies readable UI choices and `ValidateName` applies the shared Windows filename rules. An unknown saved style falls back to the current default. The entered valid version is retained in the output filename, while `InputRules.PackageVersion` separately produces four-part metadata.

`WizardPaths` holds the pure text rules behind the wizard's editable path fields: `NormalizePathText` trims whitespace and one pair of surrounding quotes from typed/pasted paths, `SamePath` compares paths case-insensitively, and `ReconcileSuggestion` decides whether a chosen destination follows a moved suggestion (it does only while it still echoes the previous suggestion; a diverged custom path is left alone).

Windows .NET 10 input contracts and filesystem validation, shared by the wizard and packaging services. Original AppWrap code uses the repository's MIT license; there are no third-party package dependencies.

Public API: immutable `AppWrapInput`, `OutputMode`, `UserInputException`, and `InputRules` (`Validate`, `Executables`, `PackageVersion`, `SafeId`, `SafePath`, `IsWithin`, `Text`). Validation and executable discovery read the selected local filesystem; they do not run applications, write settings, start processes, or use the network. Importing the assembly has no background side effects. Exceptions describe rejected paths and inputs.

```csharp
using AppWrap.Core;
var input = new AppWrapInput(source, "My App", "1.2", "MyApp.exe", true, false, output);
InputRules.Validate(input);
var fourPartVersion = InputRules.PackageVersion(input.AppVersion); // 1.2.0.0
```

The final optional positional argument `StandardOptions` accepts `StandardInstallerOptions(OfferLaunchAfterInstall = true, OfferStartWithWindows = false, OfferDeveloperWebsite = false, DeveloperWebsite = null)`. Existing calls retain these defaults. `StandardInstallerOptions.Normalize(null)` returns those defaults; when the website offer is enabled it returns a normalized absolute HTTP/HTTPS URL or throws `UserInputException`. `ValidateWebsite` rejects credentials, raw quotes/backticks, control characters, whitespace, backslashes, relative/custom schemes and values over 2048 characters. These two methods perform no filesystem or network I/O. Portable inputs ignore this standard-only option, including when paired with a standard input carrying different options.

```csharp
var standard = input with { StandardOptions = new(false, true, true, "https://example.org/app") };
InputRules.Validate(standard);
```

## PortableProfiles (P0–P6 automatable parts)

`AppWrap.Core.PortableProfiles` began as the configuration-only first slice of portable profiles; P1 adds the real PAL path on top of it. The final optional positional argument `Profile` on `AppWrapInput` accepts a `PortableProfile`; `null` (the default) retains the existing packaging-only behaviour, and a `Pal` profile is only meaningful for portable packages (the standard build rejects it). `PortableLauncherGenerator` (in `AppWrap.Generators`) serializes the profile into the launcher INI — defaulting `ProgramExecutable` to the payload executable under `Payload\` and refusing rooted, parent-escaping or non-payload targets — and derives the pinned compiler's conditional defines, and `PalCompiler` (in `AppWrap.Build`) compiles a real root PAL launcher with the hash-pinned backend (see the `AppWrap.Build` README). Evidence level: **Configuration validated; PAL compilation requires the pinned Windows backend and is Unverified on non-Windows hosts** — the bundled `makensis.exe` is a Windows binary, so no PAL compile is claimed from non-Windows evidence. `IniDocument` is a lossless ordered INI AST that preserves comments, blank lines, repeated keys (including repeated `-` discard rows) and the original line endings, round-tripping unedited text byte-for-byte while collecting parse issues instead of throwing on content. `PortableProfile` (schema version 1) carries the execution kind, the pinned `EngineLock` (PAL 2.2.9 / NSIS 2.46.5-Unicode, hash-pinned), launcher/installer/metadata/user-override documents, assets and trusted extensions; `PortableProfile.PackagingOnly()` retains the existing packaging-only behaviour. `PortableProfileCodec` imports/serializes INI text inertly — imported content never grants trust (`TrustedExtension.Trusted` stays false unless set by an explicit in-product action). `CapabilityCatalog` is the versioned pinned-PAL key/section/token knowledge, and `PortableProfileValidator.Validate` returns ordered `ProfileDiagnostic` values (unknown/deprecated/unsupported keys, duplicate singletons, sequential gaps, section-case, uncovered registry writes, unsafe wait/force-cleanup combinations, broad registry/directory targets, unknown or forward-referenced tokens, and control characters). P2/P3 add the full typed launcher surface on top: `ProfileRules.From` derives ordered typed views from the launcher document (launch settings with PAL defaults, file/directory move rules including the `-` protect-local form, registry key and value-write rules parsed with the exact pinned PAL format, environment assignments, FileWrite rules, and language settings) — derived views only, never a second persisted model — and `ProfilePlanner.Prepare` builds an immutable `PreparedPlan` (ordered planned operations with plain-language summaries, required Data parents to stage from DefaultData, PAL host backup locations, and wait/XML/compile-force flags) only when validation has no errors, adding cross-rule diagnostics for moving `Data\settings`, overlapping move targets, force cleanup overlapping a restore scope, environment reference cycles, FileWrite rules without a file, and XML file/language rules without `[Activate] XML=true`. Evidence level is unchanged: **Configuration validated** — planning and typing are pure configuration work, and runtime portability still requires the Windows fixture suite. P4 adds the installer surface on the same terms: `InstallerRules.From` derives typed views from the profile's installer (installer.ini) and metadata (appinfo.ini) documents — preserve/remove lists, [MainDirectories] switches, the optional-components family, installer languages, the download and copy-local families, legacy versions, plugin/common-files mode, and the full metadata record (details, license, version, dependencies, control starts) — and `InstallerValidator.ValidateInstaller` checks them: the trusted upgrade guard's own installer settings cannot be set by a profile at all (`GuardSettingOverride`; the guard's values always win in the merged document), preserve/remove lists obey the upstream 10-item limit with no preserve/remove overlap and no remove target inside `Data`, `RemoveDataDirectory` is rejected as not part of the current published format, optional payload entries require `OptionalComponents=true` and a known or metadata-declared install type, a [Languages] section must keep `ENGLISH=true` (unknown language keys only warn), metadata AppID conflicts with the wizard-derived identity and non-numeric package versions are errors, and the download, copy-local, legacy-version and plugin families — all of which can act before the existing PreInstall guard — are typed and discoverable but blocked with `GuardOrderBlocked` until the reviewed earlier-safe guard order (the internal AppWrapPreMutation gate) exists; download URLs and SHA-256 hashes are still configuration-checked while blocked. Evidence level is unchanged: **Configuration validated**. P5 adds the workspace behind the wizard's `Portable behavior` step (Portable/Both only, after executable selection): `ProfileWorkspaceState` holds the mode choice and the kept-in-session working profile — switching between `Already portable` and `Configure data and cleanup` never discards edits, and `EffectiveProfile` is what the wizard passes to the portable build (`null` for packaging-only) — and derives everything the WPF workspace shows from the same documents: the ten contract categories with their runtime or installer column sets (never mixed), paged rule rows enriched from the typed views, and the combined planner + installer diagnostics (the P4 blocked families appear as visibly blocked rows, and any error blocks the wizard from continuing). Structured edits go through the same documents: value/key edits, sequential and numbered-list add/remove/reorder with gap-free renumbering (including `-` discard rows and whole-section FileWrite swaps), raw-text editing that retains an invalid draft as diagnostics instead of discarding it, force-cleanup acknowledgment, and profile New/Load/Save to user-selected files — the saved format carries the documents as their codec INI texts and deliberately never serializes trust, so an imported extension is always untrusted until `SetExtensionTrusted` is invoked as an explicit in-product action. The GUI step uses the existing themes (including high contrast) and the 680×560 minimum-size layout with a compact workspace header; evidence level is unchanged: **Configuration validated** — the WPF workspace builds under EnableWindowsTargeting, and its actual layout and interaction on Windows remain Unverified. P6's automatable part adds no Core surface: the generated source/license bundle is written by `AppWrap.Build`'s `PalSourceBundle` (see the `AppWrap.Build` README), and the per-phase, per-family qualification record — including everything that remains Unverified and why (the host runtime fixture suite, guard-variant and PAL-cleanup runtime waits, an actual PAL compile, WPF layout on Windows, and the independent final review) — lives at `docs/portable-profiles-qualification.md`.

## Projects (Development Suite Phases 1–5)

`AppWrap.Core.Projects` is the persistent PAF project model. `PafProject` is the versioned `appwrap.project.json` document (current schema 3: name, targeted PAF spec version — `3.9`, the version PortableAppsGenerator emits and the pinned Installer 3.9.24 implements — creation time, source snapshot hash, build mode history, user choices, and the project's icon and sidebar image paths), with unknown JSON properties preserved verbatim through round-trips via extension data. The image properties are stored project-relative in forward slashes when the file lives inside the project root and absolute when it does not (`ProjectStore.ToStoredPath` / `ResolveStoredPath`); `PafValidator` checks them field-by-field (missing file, escaping relative path, unsupported picture type, the imaging layer's 32 MB bound). `ProjectStore` loads, saves (atomically) and infers projects: a folder without a project file yields an inferred project whose name and spec version come from an existing `App/AppInfo/appinfo.ini` when present — and whose icon is inferred from the conventional `App/AppInfo/appicon.ico` when the folder carries one (the sidebar has no conventional in-package location and is never inferred) — and `RecordBuild` appends a completed build mode and refreshes the snapshot. Schema migration is a forward-only chain (`ProjectMigrator`): the v1 shape (`schemaVersion`, `name`, `pafSpecVersion`, `createdUtc`) gains the v2 fields as empty defaults, v3 adds the two image properties as absent/null, and a newer-than-current schema is rejected rather than downgraded. `SourceSnapshot` computes a deterministic SHA-256 over the tree (ordinal relative paths, per-file size and content hash) bounded by the build layer's own source limits (50,000 entries, 40 nested folders, 20 GB), returning a truncated marker instead of a partial hash when a bound is hit; the root project file is excluded because it records the hash. `PafLayout` holds the canonical layout constants grounded in the pinned toolchain (notably `App/AppInfo/installer.ini`, `App/AppInfo/Launcher/<AppID>.ini`, `Other/Source/PortableApps.comInstallerCustom.nsh`). `PafValidator.Validate` returns ordered `PafDiagnostic` values (severity, stable code, project-relative file path, INI section/key, message, remediation hint): existing files are validated field-by-field with errors for broken fields, while absent canonical files are Info/Warning because AppWrap generates them during packaging. Payload safety: `BuildService.Snapshot` skips exactly the root project file (via the shared `ProjectStore.IsProjectFileName` predicate) so project state never enters a package. The full contract is documented in `docs/project-model.md`. Evidence level: **Configuration validated** — model, migration, snapshot and validator are covered by the check harness; wizard persistence wiring builds under EnableWindowsTargeting and its interactive behaviour on Windows remains Unverified.

Phase 2 adds the configuration surface on the same model: `ProjectConfigWorkspace` is the testable state behind the wizard's project configuration panel. It loads the project's three INI documents (appinfo, the AppID's launcher INI, installer.ini) through the lossless `IniDocument` — the files on disk are the single source of truth — and exposes a guided field catalogue grounded in what AppWrap emits and validates (PortableAppsGenerator's appinfo document and the `InstallerRules` metadata surface; the pinned PAL 2.2.9 launcher catalogue including `[LiveMode] CopyApp`, which the pinned RunLocally segment reads — `CopyData` was removed by PAL 2.2.9 and is not offered; the installer document's scalar keys, with the numbered preserve/remove lists left to the text view). Field and text edits mutate the same parsed documents, so unknown sections, keys, comments and ordering survive; `Save` writes only changed documents, refreshes the snapshot and persists the project. The workspace also carries the project's image properties (`IconPath` / `SidebarImagePath` accessors in stored form, `ImageFieldStates` with resolved path, existence and attached diagnostics) behind the panel's Project tab. Validation reuses `PafValidator` unchanged — the workspace passes its in-memory documents as an optional overlay so unsaved edits validate under the identical rules, and diagnostics attach to fields by file/section/key. To support that overlay, `PafValidator.Validate` gained one optional parameter (in-memory document texts keyed by display path); no rule changed and disk-only callers are unaffected. Advanced mode is a per-project flag persisted in the project file's user choices (`advancedMode`), off by default and off for inferred projects; it gates only direct text editing of the project's two custom-code files (`Custom.nsh`, `PortableApps.comInstallerCustom.nsh`), with writes refused as a typed `CustomCodeWriteOutcome` when off. It changes no packaging behaviour: source build scripts in a payload remain rejected and source custom code is never compiled or executed. Evidence level: **Configuration validated** — the workspace, round-trips, diagnostic attachment and the Advanced gate are covered by the check harness; the WPF panel builds under EnableWindowsTargeting and its layout/interaction on Windows remains Unverified.

Phase 3 adds the third output mode, `OutputMode.PafPackage`: the destination is a package folder rather than an `.exe` file, so `InputRules.Validate` applies folder rules to it (no `.exe` name, not an existing file, may not contain the application folder) while the file modes' rules are unchanged. `PackageNaming.GetFolderName` derives the canonical PAF folder name — the AppID, identical to `PortableAppsGenerator.PackageId` — used for the wizard's folder preview and destination. The build-layer half of the phase (staging and transactional folder publication) is documented in the `AppWrap.Build` README and `docs/PAF-COMPLIANCE.md`.

Phase 5 adds project creation: `ProjectScaffolder.CreateBlank` writes a minimal valid PAF skeleton (canonical layout, placeholder appinfo/installer/launcher INI documents, and an `appwrap.project.json` recording the template origin under the `template` user choice and the targeted PAF spec version, defaulting to 3.9) into a new or empty folder — staged in a sibling temporary folder and moved into place only when complete — and returns the created project with its `PafValidator` diagnostics. Required fields carry valid placeholders (a conventional derived AppID, `PackageVersion=1.0.0.0`, `Start=<AppID>.exe`), so a fresh scaffold validates with zero errors; values that still need the author carry TODO markers, which the validator reports as `TodoPlaceholder` warnings naming the exact file/section/key (an additive Phase 5 rule in `PafValidator` — it changes no existing severity). Custom-code starter files are scaffolded only when the project's Advanced mode is on; both starters are comment-only, and their headers state honestly how each file is consumed (the launcher's `Custom.nsh` is included by PAL when a launcher compiles from a portable profile; a source-supplied installer hook is still rejected by AppWrap packaging). The "Wrapped binary" template writes no tree: it is the existing wrap-a-folder inference path, and `ProjectStore.LoadOrInfer`/`Infer` accept an optional template name recorded only on newly inferred projects. Evidence level: **Configuration validated** — scaffolding, TODO diagnostics, destination discipline, template recording and editor-open are covered by the check harness; the WPF panel builds under EnableWindowsTargeting and its layout/interaction on Windows remains Unverified.

## TestHarness (Development Suite Phase 4)

`AppWrap.Core.TestHarness` is the pure half of the runtime test harness: nothing in it launches a process. `TreeSnapshot` captures a watched root as a deterministic file list with per-file size and SHA-256 (bounded by the build layer's own source limits — 50,000 entries, 40 nested folders, 20 GB — with linked entries rejected via `InputRules.SafePath`) and diffs two snapshots into Created / Modified / Deleted changes. `WriteClassifier` classifies each change by watched root: under the package copy's `Data/` is the expected portable write; elsewhere in the package copy is a noted package-root write; anything in the redirected profile root is profile leakage and a portability violation; the redirected temp root is noted scratch. Its verdict is Pass only for a run that exited by itself with code 0, did not time out, and produced no violation. `TestReport` is the versioned `test-report.json` model (schema 1, camelCase, string enums): app name, mode (`Portable` / `PafPackage`), launch command, start time, duration, exit code (null when killed), timed-out flag, all detected writes, the violation subset, and the verdict, with a JSON round-trip. The launching half — sandbox copy, environment redirection, the graceful-then-force timeout, and cleanup in all exit paths — is `AppWrap.Build`'s `TestHarness`, and the full contract and limitations (coarse snapshot detection, no registry observation, no clean-machine guarantee) are documented in `docs/TEST-HARNESS.md`. Evidence level: **Configuration validated** — the model, classifier, snapshot diff and the whole pipeline over a stub runner are covered by the check harness; real end-to-end launches are covered only by the Windows test suite (`TestHarnessAsyncChecks`) and remain Unverified from non-Windows evidence.

Use `tools/Test-PackedModules.ps1` from the repository for an independent consumer restored from the actual local NuGet artifacts. The application regression harness covers additional malicious paths and input cases. These are local APIs for trusted host applications; validation cannot eliminate all filesystem change races.
