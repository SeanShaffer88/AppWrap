# AppWrap

## TL;DR

AppWrap is a PortableApps.com development suite and guided package creator for Windows. A native wizard wraps an application folder into a standard installer, a portable package, both, or an uncompiled PAF Package folder; around it sit a PAF project model with guided configuration editors, a portable launcher profile workspace, project templates, and an explicit runtime test harness. A full command-line interface (`AppWrap.Cli.exe`) exposes every one of those capabilities to scripts and local AI operators. No accounts, downloads or telemetry in the application; project editing is configuration bookkeeping only, and custom code stays behind an off-by-default Advanced mode (see Limits).

**Release status:** the latest GitHub release is **v0.2.4**. Complete on `main` since then and shipping as **v0.2.5**: the design now conforms to **FluentGruv v1.3.0** — FluentGruv dark is the default theme, FluentGruv Light second, the palette extended token-for-token against the spec, with radii, spacing, and fonts per spec; until that release is cut, building from source (see Build and verify) is the way to get it.

**Evidence levels** (the vocabulary of `docs/ROADMAP.md`): **Verified** — an automated check ran and passed in the named environment; **Configuration validated** — model, validation and build-boundary logic implemented and check-covered on a non-Windows host, with no Windows compiler or runtime involved; **Unverified** — not exercised in the available environment. Windows runtime behaviour, an actual PAL compile, WPF layout, and compilation of a PAF Package folder by the official installer remain **Unverified**; the qualification work is a planned ROADMAP item.

## What it does

- **Wizard** — choose a folder, answer six, seven or eight questions, and build an **Installer**, **Portable app**, **Both**, or **PAF Package**. Every folder and save-location field accepts typed or pasted paths as well as browsing, and **Package another app** on the final page resets to a fresh first page.
- **PAF project model** (Development Suite Phase 1) — every chosen folder gains an `appwrap.project.json` (schema v3, targeted PAF version, source snapshot, build history, saved choices, and the project's icon and sidebar images as first-class properties), validated field-by-field. The wizard's configuration panel edits its appinfo, launcher and installer documents with inline checks, plus the project images on a Project tab. Advanced mode (off by default, per project) alone unlocks direct `Custom.nsh` text editing. **Configuration validated.**
- **Portable launcher profiles** (profiles roadmap P0–P6) — for portable outputs, a profile workspace edits the launcher's rules (file/directory moves, registry save/restore, services, environment, and more) over a lossless INI model, with a capability catalogue, strict validation, and a previewed operation plan; PAL packages are built with the pinned, hash-verified PortableApps.com Launcher backend and carry its corresponding-source/license bundle. **Configuration validated**; PAL compilation and runtime behaviour on Windows **Unverified**.
- **PAF Package output** (Phase 3) — the uncompiled package folder for the official PortableApps.com Installer, sharing staging with the compiled portable output; their generated documents are byte-identical. **Configuration validated**; compilation of the folder by the official installer **Unverified**.
- **Runtime test harness** (Phase 4) — an explicit **Test package…** action runs a finished portable or PAF package once in a throwaway sandbox and reports where it wrote — files and, via before/after snapshot diffs of the HKCU/HKLM `Software` roots, the registry; builds themselves never run a packaged app. **Configuration validated** for the report/violation logic; real-app runs on Windows **Unverified**.
- **Portable-conversion audit** — **Convert a setup or zip…** audits a setup `.exe`/`.msi` or portable `.zip` to learn where the app stores data and which registry entries it creates: a read-only static pass, an optional explicit runtime pass, and a draft portable profile for review — never auto-trusted (see `docs/AUDIT.md`). Runtime actions in the wizard use Sandboxie; a zip's selected app can run there and its extracted payload is kept for the next build. A missing Sandboxie install or registry-hive error stops the sandbox audit; it never falls back to the host. **Configuration validated**; Windows runtime behavior **Unverified**.
- **Four-stage conversion pipeline** — the audit, extended (`docs/PIPELINE.md`): AppWrap Setup bootstraps the pinned x64 Sandboxie-Plus release; pinned extraction engines (7-Zip, innoextract, lessMSI) unpack installer payloads for the static pass; sandboxed profiling harvests file and registry changes; drafts gain vendor-folder cleanup and `[FileWrite]` path-repair rules plus a composited branding splash; and the test harness verifies zero writes escape a clean Sandboxie box. AppWrap supports Windows 11 x64 only. **Configuration validated**; all Windows runtime behavior **Unverified**.
- **Templates** (Phase 5) — **New project from template…** scaffolds a blank PAF project that validates cleanly (placeholders surface as TODO warnings) or records a wrapped-binary project from an existing folder. **Configuration validated.**
- **Compliance documentation** (Phase 6) — `docs/PAF-COMPLIANCE.md` states exactly how the outputs relate to the official toolchain, and `ComplianceChecks` pins its matrices to the generator output, the editor field catalogue and the capability catalog so a supported field cannot regress silently.
- **Command line** — the CLI mirrors the wizard and suite command-for-command, with `--json` output and defined exit codes (see Command line below and `docs/CLI.md`). Since the dual-mode restructure it lives inside `AppWrap.exe` itself; `AppWrap.Cli.exe` is a tiny native shim that forwards to it, so the two entry points are interchangeable. **Configuration validated**; real packaging runs on Windows **Unverified**.
- **Project image properties** — the icon and sidebar image belong to the project, not to one build: reopening a project restores them, a build records the effective picks back, the editors and the CLI (`config … project Images …`) reach them, and the validator checks the referenced files. The sidebar applies to the compiled portable package only — the official installer has no package-side sidebar, so a PAF Package folder never carries one (see `docs/PAF-COMPLIANCE.md`). **Configuration validated**; WPF interaction on Windows **Unverified**.

## Run

Use Setup for the full Windows x64 install; it installs Sandboxie from the embedded, hash-verified installer, so setup works offline. Windows still asks for UAC approval to install Sandboxie's kernel driver. The complete ZIP also includes the .NET runtime and AppWrap's packaging engines, but does not install Sandboxie into Windows; sandboxed profiling needs Setup to run once. Users do not install .NET, Inno Setup, NSIS, or PortableApps tools separately. Keep `third_party` and the accompanying runtime files beside the executable. AppWrap is unsigned.

Choose **Installer**, **Portable app**, **Both**, or **PAF Package** on the first page. Every folder and save-location field in the wizard can be typed or pasted into directly, as well as chosen with its browse button; pressing Enter or moving on commits a typed path through the same checks as a browsed one. To start from scratch instead of wrapping a folder, choose **New project from template…** on the first page: the **Blank PAF app** template scaffolds a minimal valid project (placeholder values marked TODO are listed as warnings) into a new, empty folder and loads it for editing, and the **Wrapped binary** template is the same choose-a-folder flow with the template recorded in the project file. Scaffolding writes project files only — it never builds or runs anything. Installer, Portable app and Both are AppWrap's own compiled outputs (the generated portable installer is the AppWrap Installer); **PAF Package** instead produces the uncompiled package folder for the official PortableApps.com Installer to consume — see `docs/PAF-COMPLIANCE.md` for the exact relationship. The name comes from the folder, the default version is `1.0`, and a sole executable is selected automatically. Optional shortcut selections default Start Menu on and Desktop off; the installing user can change them. Portable packages use their portable menu entry instead of creating Windows shortcuts. Optional pictures can be skipped; the icon and sidebar steps show the project's recorded pictures when a project supplies them, and a build records the pictures actually used back into the project file. The sidebar step appears only for the compiled portable outputs — a PAF Package has no sidebar image, because the official installer compiles with its own installation's sidebar bitmap. Standard installers can offer app launch (default on), Start with Windows (default off), and a developer website (default off) on completion. The website URL is validated locally and starts unchecked in setup; startup changes only when the user finishes. Website text is cleared when selecting another application. Installer uses six steps, Portable app and PAF Package seven, and Both eight. Both uses one shared source, one destination folder, and one Build button to produce both files from one source snapshot. A PAF Package build asks for a destination folder and creates the package folder (named after the app's AppID) inside it.

The final step offers `Name-Version-Setup` (default), `Name_Setup`, and `Name-Setup-Version` filename styles with actual filename previews. A single-format save dialog also permits a custom filename, and the destination itself can be typed or pasted. When the name, version, mode or style changes, a chosen destination that still matches the previously suggested filename follows the new suggestion; a custom filename that has diverged from the suggestion is kept as typed. Before replacing existing output, AppWrap shows one confirmation naming the targets. When a package is ready, **Package another app** on the final page returns to the first page with all per-app state cleared — nothing is saved or carried over — so another program can be packaged straight away. Content identities are captured before confirmation and checked again before publication, so stale consent cannot replace changed files.

Both outputs are prepared before either destination is changed. A handled second-file failure rolls the first back, or reports precise recovery paths if rollback is blocked. Cancellation is deferred during that short commit/recovery operation. This is not an atomic two-file transaction across process termination or power loss: recognizable `.appwrap-*.backup` and `.appwrap-*.tmp` files may remain beside the destination. Review those recovery files before deleting them; details identify the exact backup after a handled failure. A PAF Package folder is published with the same discipline: the staged folder is copied to an owned `.appwrap-*.tmp` folder beside the destination and verified against its tree hash, any previous package folder is moved to an `.appwrap-*.backup` folder, and a handled failure restores it.

For portable outputs, the wizard's portable behavior step opens the profile workspace: the launcher rules that make an app portable — which files and folders move between the package and the host, which registry keys are saved and restored, environment variables, services, and cleanup behaviour — are edited as typed rules over the package's launcher configuration, checked against the profile validator as you work, and previewed as an operation plan before building. Profiles save and load as files; importing a profile never grants it trust, and a profile with validation errors stops the build before anything is written. Some installer-side rule families remain visibly blocked until the reviewed `AppWrapPreMutation` gate exists (see `docs/ROADMAP.md`); they are never silently dropped.

Portable mode is for an application that already supports portable use. AppWrap does not redirect registry/profile writes, change dependencies or certify host cleanup. The complete original folder is retained under `App/Payload`, with a small native launcher that preserves its relative dependencies, working directory and caller arguments. The packaged application is never run during a build. Unknown license information is retained as unknown/conservative metadata; packaging does not grant redistribution rights.

At installation, portable packages gracefully close the selected destination's main executable and AppWrap launcher before replacing payload files. Exact image paths determine ownership: another folder's same-name app is left running. Applications that refuse to close, have an unsaved-work prompt, or cannot be identified stop the upgrade after a bounded wait. Nothing is force-killed or restarted. Other child programs/services require application-specific handling. The official generated installer uses an original trusted AppWrap preinstall hook; arbitrary source hooks remain rejected. See `native/UpgradeGuard/README.md`.

## Command line

AppWrap is dual-mode: one self-contained `AppWrap.exe` is both the wizard and the CLI. `AppWrap.Cli.exe`, a tiny native shim beside it, forwards its arguments to `AppWrap.exe` and propagates the exit code — and `AppWrap.exe` accepts the same command line directly (`AppWrap.exe build …`); with no arguments it opens the wizard. Either entry point exposes every wizard and suite capability as commands — package a folder (`build`, all four modes), validate and inspect projects (`project validate|info|create`), read and edit project configuration (`config list|get|set`, including the `project` document's image properties), validate portable profiles (`profile validate`), run the test harness (`test`), and audit a setup file or portable zip for conversion (`audit`, with `build --audit-draft` for a reviewed draft profile) — so scripts and local AI operators can drive AppWrap without the GUI. With `--project`, a build takes its default name, filename style, icon and sidebar image from the project (explicit flags override them) and records the completed build and the effective image picks back, as the wizard does. Every command accepts `--json` (one envelope object with the result and structured diagnostics) and `--verbose`; exit codes are 0 success, 2 usage error, 3 validation failed (nothing written), and 4 build/test failure. The CLI resolves its packaging backends from its own folder exactly like the GUI. Full reference: `docs/CLI.md`.

```powershell
appwrap build --source C:\Apps\ListSorter --mode both --output D:\Packages --json
appwrap project validate C:\Apps\ListSorter
appwrap test D:\Packages\ListSorterPortable --mode portable
```

## Appearance and state

Choose FluentGruv, FluentGruv Light, AppWrap, Catppuccin Mocha, Nord, Gruvbox Light or OLED Black in the Appearance list beside Exit. FluentGruv (dark) is the default and implements SEAN's FluentGruv design system token for token — see `docs/DESIGN.md`. These are native brush palettes; Windows high-contrast mode uses system colors. Window size, theme and preferred filename style are stored in `Data/window.json` beside AppWrap. Restoring bounds conservatively clamps to the primary monitor's work area, so secondary-monitor positions may move to the primary monitor after restart.

Build staging lives in `Data/Builds/<unique-id>` and is removed after each normal build/cancel/failure. If cleanup fails, the UI identifies retained owned paths in details. A crash or power loss can leave staged copies; with AppWrap closed, `Data/Builds` may be deleted. Removing the extracted AppWrap folder removes its own settings and bundled tools. Windows may independently record ordinary application execution history. No hidden monitoring or background service is installed.

## Limits

Local regular paths only; linked/reparse paths are rejected. Sources are bounded to 50,000 entries, 40 nested folders and 20 GB. Pictures are bounded to 32 MB, 8192 pixels per side and 32 megapixels. Printable app names and numeric versions with one to four components are accepted. Compiler grammar-special path characters may be rejected with an actionable error. Portable source custom build scripts are unsupported and rejected; source installer actions/download settings are never executed. Optional chosen images produce seven ICO frames, PNG companions and a 164×314 24-bit sidebar bitmap (the sidebar bitmap is used by the compiled portable installer only; it is not part of a PAF Package folder).

Standard installers use a stable app-name-derived per-user installation identity, offer application launch on completion and ask the installer engine to close files in use. Runtime install/upgrade/uninstall, clean-machine compatibility and arbitrary application portability require testing; compilation and static archive checks do not establish them. Portable upgrades preserve unlisted files in `App`/`Other`/`Data`; files shipped with the same path can still be replaced, so application-specific settings behavior remains the app's responsibility.

Choosing a folder now records an `appwrap.project.json` project file at its root (schema, targeted PAF version, source snapshot hash, build history, saved choices, and the project's icon and sidebar image paths; see `docs/project-model.md`). Projects created from the blank template record their template origin the same way, and their unfinished placeholder values are reported by the project validator as TODO warnings, never errors. The file is AppWrap bookkeeping only: it is excluded from every package payload, and folders without one behave exactly as before. The wizard's project configuration panel edits the project's appinfo, launcher and installer configuration with the format checks shown inline, and its Project tab edits the icon and sidebar image properties with the same checks. Advanced mode is off by default, is recorded per project in that file, and only unlocks direct text editing of the project's own `Custom.nsh` and `PortableApps.comInstallerCustom.nsh`; it changes no packaging behaviour — source build scripts in a payload are still rejected and custom code from a source folder is still never executed or compiled into a package.

After a portable or PAF Package build, the wizard offers a **Test package…** panel (see `docs/TEST-HARNESS.md`): an explicit, separate action that runs the packaged app once in a throwaway sandbox with a redirected profile, reports where it wrote in `test-report.json`, and flags profile writes as portability violations. Builds never execute a packaged app — testing happens only from that panel — and detection is coarse snapshot diffing of files and the HKCU/HKLM `Software` registry roots; no clean-machine guarantee is made.

## Build and verify

Windows x64, PowerShell 7, .NET SDK 10.0.404 or a compatible .NET 10 SDK, and the pinned runtime backend folders are required to build a release. No third-party NuGet runtime packages are used.

The checked native upgrade helper is embedded in AppWrap.Build. To rebuild it from source first, run `native/UpgradeGuard/Build.cmd` from that directory using the documented installed MSVC19.44/SDK10.0.26100.0 environment, then rebuild the .NET solution. Its compiler is a development dependency; generated installers carry the x86 static-runtime helper and require no compiler or .NET installation. Source, recipe and exact build provenance accompany the runtime distribution.

```powershell
dotnet build AppWrap.sln -c Release
& AppWrap.Tests/bin/Release/net10.0-windows/AppWrap.Tests.exe $PWD.Path 'C:/Program Files/FileBot/lib/7z.exe'
pwsh -NoProfile -File tools/Test-PackedModules.ps1
pwsh -NoProfile -File tools/Build-AppWrap-Setup.ps1
```

`Build-AppWrap-Setup.ps1` prepares the pinned Sandboxie backend, publishes a self-contained x64 payload, and compiles Setup with the NSIS compiler already in the PortableApps backend. It does not require a separate NSIS installation. Inno Setup, PortableApps, and PAL runtime backends must already be prepared; missing required files stop the build. `Publish-AppWrap.ps1` can still be run alone to produce only the payload. The optional second test argument selects an installed 7-Zip executable for static package extraction. Tests create bounded owned fixtures outside the repository and never run generated installers or payloads. `tools/Test-PackedModules.ps1` verifies all four library packages through an independent consumer and an isolated package cache. See `docs/architecture.md` and each module's README for contracts.

Backend modifications are restricted to the distinctly named silent **AppWrap Packaging Builder**, based on the upstream wizard. Its exact source, original source, patch and reproducible preparation script accompany the backend. The official generated-installer script remains unchanged. Consult `THIRD-PARTY-NOTICES.md` before distributing third-party components or generated packages commercially. AppWrap is not endorsed by PortableApps.com.
