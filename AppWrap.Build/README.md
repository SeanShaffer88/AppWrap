# AppWrap.Build

Windows .NET 10 packaging orchestration. Depends on `AppWrap.Core`, `AppWrap.Generators`, and `AppWrap.Imaging`; original AppWrap code uses the repository's MIT license. Compiler distributions are separate, versioned tools with their own licenses and provenance. They are not embedded in this NuGet package.

The original native x86 selected-destination upgrade guard **is** embedded as a build resource. It runs only inside a generated portable installer when its installing user starts installation; importing this library or building a package does not execute the guard. It has a bounded graceful-close contract, no force termination, and no .NET/external CRT dependency. The package includes its exact source, recipe, provenance, MIT license and Microsoft static CRT notice under `native/UpgradeGuard` and `licenses`. Generated packages retain these notices in their own `Other` directory, separate from the unmodified source payload under `App/Payload`.

Public API: `BuildService(baseDirectory, stateDirectory).BuildAsync(input, cancellationToken)`, `BuildResult`, `BuildFailureException`, `ProcessRunner.RunAsync(...)`, and `ProcessResult`. Construction/import has no background or filesystem side effects. An explicit build snapshots the selected source, creates temporary staging beneath the supplied state boundary, invokes the selected trusted backend, and commits output only after success. Cancellation/failure preserves existing output. The caller must supply writable, app-owned state/tool boundaries and clean up retained state after use. Payload applications are never launched by the service.

```csharp
using AppWrap.Build;
var service = new BuildService(bundledToolsRoot, appOwnedStateRoot);
BuildResult result = await service.BuildAsync(input, cancellationToken);
```

`BuildBothAsync(standardInput, portableInput, token, overwriteExisting: false, progress: null, expectedOutputs: null)` validates a matching pair and captures the original application once. Both destinations must be distinct files in the same existing folder. Optional pictures are captured once; source-contained pictures come from the same payload snapshot. `BatchBuildResult` contains both ordinary results and cleanup warnings. Generators still consume the two existing `OutputMode` values.

For an interactive host, call the synchronous hash helper off the UI thread, then obtain user replacement consent, and pass the immutable identities into the build:

```csharp
OutputIdentity[] expected = await Task.Run(() => new[] {
    OutputIdentity.Capture(standardInput.OutputPath),
    OutputIdentity.Capture(portableInput.OutputPath)
});
// Host confirms replacement of existing targets here, before authorizing true.
BatchBuildResult both = await service.BuildBothAsync(standardInput, portableInput,
    cancellationToken, overwriteExisting: true, expectedOutputs: expected);
```

The default refuses existing targets. The trusted-host `overwriteExisting: true` fallback without explicit identities captures them at API entry; an interactive caller should bind pre-confirmation identities as shown. Identities are checked at entry and before publishing. The optional three-argument single-output `BuildAsync(input, token, expectedOutput)` provides the same stale-consent check without removing the original two-argument API.

Publication uses two unique sibling pending files and backups. Handled errors restore previous files when possible, preserving unrelated replacements and recovery backups on rollback failure. Cancellation is deferred during commit/rollback. This does not promise atomic paired publication after process crash/power loss or defeat an adversary concurrently modifying the same files. Failures and warnings disclose retained paths; do not automatically delete recovery backups.

## Portable profiles (P1): the PAL compiler path

When a portable input carries a `PortableProfile` with `ExecutionKind.Pal`, `PortableBuild` validates the profile (any error diagnostic stops the build with the first problems listed), writes the generated launcher INI to `App/AppInfo/Launcher/<AppID>.ini` inside the staged package, adds `Other/AppWrap-PAL-NOTICES.txt` (pinned PAL/NSIS versions and hashes, the launcher's GPL-2.0-or-later license, the upstream source URL, and — since P6 — a pointer to the accompanying source bundle described below; earlier versions of this file instead noted that the bundle was a separate gate), and compiles the root launcher with `PalCompiler` before the packaging builder runs. Compilation failure is fatal: a profile package never falls back to the basic launch shim. Packaging-only inputs (no profile) keep the shim path unchanged, and the UpgradeGuard installer settings apply to both paths.

For Pal profiles, the generated `installer.ini` is no longer the guard settings alone (P4): `PortableBuild` first runs `InstallerValidator.ValidateInstaller` (any error diagnostic stops the build, exactly like launcher validation) and then, when the profile's installer document has entries, writes `InstallerDocumentMerger.Merge(UpgradeGuardGenerator.InstallerSettings, profile.Installer)` instead of the raw guard text. The merger is deterministic and guard-first: it starts from the guard settings, overlays profile entries section by section in profile order, and skips every key the guard owns, so guard values always win even if a profile is merged without validation. Profiles with no installer entries keep the exact guard-only text, and packaging-only builds are untouched. The profile's metadata document is validated (AppID conflict, package-version shape) but deliberately does not replace the generated `appinfo.ini` in P4 — `PortableAppsGenerator` output stays canonical, and reconciling profile metadata into it is a P5 workspace concern.

Since P6, a successful PAL compile is followed by `PalSourceBundle.WriteAsync`, which writes the generated source/license bundle into the package under `Other/Source` before the packaging builder runs: the corresponding launcher source copied at build time from the prepared pinned backend (`PortableApps.comLauncher/` — the launcher script, its top-level `.nsh` includes, `Segments/`, `Languages/`, and the `Plugins/` binaries its `!addplugindir` directive makes available; the backend's wizard/generator files are not part of the compile and are not bundled), this package's exact generated launcher INI, merged installer.ini and appinfo.ini (`AppWrap-Generated/`), and a build recipe (`AppWrap-BUILD-RECIPE.md`) recording the pinned PAL/NSIS versions and hashes, the source and download URLs, the `Prepare-PalBackend.ps1` preparation command, the exact makensis argument array (built once in `PalCompiler.BuildArguments`, shared by the compile and the recipe so they cannot drift), and a per-file SHA-256 inventory. License texts travel with the bundle: the GPL v2 text is copied from the backend's `Other/Source/License.txt`, and the NSIS `COPYING` plus the NewTextReplace readme are copied into `PluginNotices/` when the backend ships them (the pinned backend ships no separate license/readme for the UAC or XML plugins, and the recipe says so rather than inventing one). Writing is deterministic and fail-loud: every required backend source item is checked before anything is written, and a missing one fails the build with no partial bundle; the single exception is the GPL text file, whose absence is handled by stating in the notices where the GPL text lives upstream instead of fabricating license text. The established `Other/AppWrap-PAL-NOTICES.txt` path is retained and now points at the bundle. Evidence level: configuration validated — the bundle writer is covered by fake-backend checks, but no real bundle inside a real package exists yet, because that requires an actual PAL compile on Windows (see `docs/portable-profiles-qualification.md`).

`PalCompiler` is a direct adapter for the official PortableApps.com Launcher source — no interactive Generator wizard and no shell fragments; arguments are a separate argv array built by `PalLaunchArguments` in the exact pinned order (`/O<log>`, `PACKAGE`, `NamePortable`, `AppID`, `Version`, conditional `XML_ENABLED` / `RUNASADMIN_COMPILEFORCE`, launcher script last). The backend lives in `third_party/pal` beside AppWrap and is **prepared locally, never committed**: run `tools/Prepare-PalBackend.ps1` (optionally with `-ArchivePath` for an already-downloaded archive and `-SevenZipPath` when 7-Zip is not on `PATH`). The script downloads the official PAL 2.2.9 archive through the portableapps.com redirect flow, verifies its SHA-256 against the pin, extracts it statically with 7-Zip (the archive is never executed), copies `App/NSIS`, `Other/Source` and any `App/AppInfo` into `third_party/pal`, verifies the bundled NSIS 2.46.5-Unicode `makensis.exe` hash, and writes `third_party/pal/provenance.json`. At build time `PalCompiler` re-verifies the `makensis.exe` hash against `EngineLock.Pinned` before running it and requires a root launcher larger than 10,000 bytes next to the bounded compiler log; a missing or unpinned backend is a build failure, not a degraded build.

`ProcessRunner` is a low-level trusted-tool adapter, not a sandbox. It uses argument arrays, bounded logs and deadlines, and Windows Job Object cleanup. Its immediate post-start job assignment has a documented startup race; do not launch untrusted programs through it. Build error details are intended for an explicit diagnostic disclosure.

## Test harness (Development Suite Phase 4)

`TestHarness.RunAsync` is the runtime test harness — a separate, explicit user action (the wizard's Test panel), never part of a build: no build path references it, and the check suite asserts that. A run validates the request, copies the package folder into a throwaway tree under the system temp folder with this layer's own bounded `BuildService.Snapshot` (same limits, same project-file exclusion), creates a sandbox profile (`AppData/Roaming`, `AppData/Local`, `Documents`) and temp folder beside the copy, ensures the copy has a `Data/` folder, and resolves the launcher from the package's `appinfo.ini` `[Control] Start` (falling back to the only root `.exe`; a package with no launchable root file is refused before anything runs). `ProcessTestRunner` starts the launcher directly with `USERPROFILE` / `APPDATA` / `LOCALAPPDATA` / `TEMP` / `TMP` redirected into the sandbox; the pure Core half (`TreeSnapshot` / `WriteClassifier`) snapshots the package copy, profile and temp roots before and after, classifies the diff, and the resulting `TestReport` is written atomically to the caller's report path before the throwaway tree is deleted in a finally block — success, failure, timeout, crash and cancellation alike, with a cleanup failure surfaced as a warning rather than hidden. The timeout (60 seconds by default) is graceful-then-force: close the main window, wait, then terminate the whole process tree. Launching sits behind `ITestProcessRunner` so the pipeline is check-covered with a stub; the real launch checks are Windows-only (`TestHarnessAsyncChecks`). The full contract, report schema and limitations are in `docs/TEST-HARNESS.md`.

Run `tools/Test-PackedModules.ps1` for package-only consumption and cancellation/output-preservation smoke checks in an independent project. The full application harness additionally verifies actual compilers. Installer execution, upgrade behavior, and arbitrary payload portability require separate qualification.

## PAF Package output (Development Suite Phase 3)

`OutputMode.PafPackage` produces the canonical PAF 3.9 package as a **folder** for the official PortableApps.com Installer to consume unchanged, instead of a compiled `.paf.exe`. The mode is additive: `PortableBuild.StagePackageAsync` is the one staging path for both portable outputs, and the compiled flow (`BuildAsync`) is staging plus the packaging-builder step, byte-identical to before for the generated `appinfo.ini`/`installer.ini`. A PAF staging differs only where a folder consumer requires it: an empty `Data/` placeholder, and the upgrade-guard helper copied beside its hook at `Other/Source/AppWrap.UpgradeGuard.exe` with the hook addressing it package-relatively (`PortableBuild.PafGuardHelperPath`) instead of via the build-machine staging path. The payload hook rejection, guard coupling (`CloseEXE=NONE` only ever with the hook), profile validation/merge and PAL/source-bundle steps are shared unchanged; launcher compilation still happens during staging (pinned PAL for profiles, the basic shim otherwise), because the official installer does not compile launchers. `BuildService.BuildPafPackageAsync` mirrors the single-file build's snapshot → prepare → publish discipline: the staged folder's identity is its deterministic `SourceSnapshot` tree hash, and `FolderArtifactPublisher` publishes it transactionally — owned `.appwrap-*.tmp` copy beside the destination, hash verification, owned `.appwrap-*.backup` move-aside of any previous folder, move into place, rollback or precise recovery paths on handled failure, cancellation deferred during commit. `FolderOutputIdentity` is the folder analogue of `OutputIdentity`; an existing destination too large to hash is refused rather than replaced unverified, and a PAF destination may not be a file, end in `.exe`, or contain the source/AppWrap folders. The full compliance statement — targeted spec version, emitted vs. omitted appinfo surface, honored vs. blocked installer.ini families, and who compiles what — is `docs/PAF-COMPLIANCE.md`. Evidence level: the tree builder and folder publisher are covered by `PafPackageChecks` without any compiler execution; compilation of the folder by the official installer on Windows remains Unverified.
